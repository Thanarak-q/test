ทุกบัญชีมีข้อจำกัด 2 ชั้น และคำขอต้องผ่านทั้งสองชั้น

| ข้อจำกัด | นับอะไร                        | Headers                                                                                |
| -------- | ------------------------------ | -------------------------------------------------------------------------------------- |
| คำขอ     | ทุกคำขอ ไม่ว่าจะใหญ่แค่ไหน     | `RateLimit-Limit`, `RateLimit-Remaining`, `RateLimit-Reset`                            |
| โทเคน    | จำนวนโทเคนโดยประมาณในแต่ละคำขอ | `X-RateLimit-Tokens-Limit`, `X-RateLimit-Tokens-Remaining`, `X-RateLimit-Tokens-Reset` |

- คำขอ: ได้สูงสุด <Value path="limits.requests.capacity" /> ในคราวเดียว และเติมคืน
  <Value path="limits.requests.refillPerMinute" /> ต่อนาที
- โทเคน: ได้สูงสุด <Value path="limits.tokens.capacity" /> และเติมคืน
  <Value path="limits.tokens.refillPerMinute" /> ต่อนาที

`-Reset` คือจำนวนวินาทีจนกว่า bucket นั้นจะกลับมาเต็ม

## ทำไมต้องมี 2 ชั้น

ถ้านับแค่จำนวนคำขอ prompt ยาวมากหนึ่งตัวจะมีต้นทุนเท่ากับคำขอเล็ก ๆ หนึ่งพันครั้ง
ถ้านับแค่โทเคน คำขอเล็กจิ๋วหลายพันครั้งก็จะผ่านไปได้ แต่ละชั้นจึงจับสิ่งที่อีกชั้นพลาด

ทั้งสองชั้นแยกกัน prompt ยาวมากแค่ห้าตัวอาจใช้ข้อจำกัดด้านโทเคนจนหมด
ขณะที่ข้อจำกัดด้านคำขอยังเหลืออีกมาก headers จะบอกว่าคุณใกล้ชนข้อจำกัดไหน

## เมื่อได้ 429

อ่าน error code เพื่อดูว่าชนข้อจำกัดไหน แล้วรอตามจำนวนวินาทีใน `Retry-After`

- `rate_limit_exceeded_requests` — ส่งคำขอมากเกินไป ให้ส่งช้าลง
- `rate_limit_exceeded_tokens` — ใช้โทเคนมากเกินไป ให้ส่งช้าลงหรือส่งให้น้อยลง
  เช่น ใช้ prompt ที่สั้นลง หรือลด `max_tokens`

## การรอก่อนลองใหม่

ลอง `429` และ `503` ใหม่หลังครบ `Retry-After` โดยสุ่มเวลาเพิ่มเล็กน้อย (jitter)
เพื่อไม่ให้ client จำนวนมากลองใหม่พร้อมกัน อย่าลอง `401` หรือ `400` ใหม่
